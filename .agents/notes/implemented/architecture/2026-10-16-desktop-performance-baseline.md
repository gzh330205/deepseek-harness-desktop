# Agent Note: 桌面端卡顿的量化定位（第三轮：根因是 dsh-genui 0.12.0 的 DOM 全量 sweep）

Status: implemented

## Problem

用户反馈「桌面端非常卡，打字都有延迟」，并在微信上打字无延迟，因此怀疑是我们的应用。这类主观描述
必须先量成数字，否则每一条怀疑（渲染进程死循环、插件轮询、文件监视、防火墙、我们的诊断代码）都会
变成一次盲改。

## Decision

量，而且**在用户正在使用的实例上量**：不重启它（我的 agent 会话就跑在那个实例里），用「空数据目录对照 +
0.5 秒粒度 CPU 采样 + I/O 计数器 + 找出活跃会话」这套组合，把主观的「很卡」变成可比较的数字。

## Method

全部在**用户正在使用的实例**上做，不重启它（我的 agent 会话就跑在那个实例里，重启会打断自己）：

1. **进程树 + 角色**：`Win32_Process.CommandLine` 分辨主进程、3 个渲染进程、GPU/网络进程，以及
   **DSH 服务子进程**（Electron 二进制 + `ELECTRON_RUN_AS_NODE` 跑 `app.asar/dsh/...`）。
2. **每 0.5 秒采样 CPU**（`Get-Process`.CPU 差分），而不是 3 秒采样——3 秒采样把 `25% → 0 → 27%` 的
   连续占用混叠成了「每 3 秒一次突发」，差点把结论带向「定时器轮询」。
3. **I/O 计数器**（`Win32_PerfFormattedData_PerfProc_Process`）：`ReadOps/WriteOps/DataOps/OtherOps`。
   读盘为 0 就能排除文件监视与扫盘这类猜测。
4. **对照实例**：用**全新数据目录**（空 home）起同一个壳，量基线的服务进程 CPU 与内存。
5. **谁在写**：找出最近 5 分钟内被写入的会话文件，确定「活跃的是哪个会话」。

## Measurements

| 对象 | CPU | 内存 | 说明 |
|---|---|---|---|
| 壳 = 全新数据目录（空 home） | **0%** | 57 MB | 壳 + 我们注入的插件 + 浏览器面板的基线：**没有忙循环** |
| 用户实例的 DSH 服务进程 | **12–25% 持续** | 386 MB | 无读盘（`ReadOps=0`，`OtherOps≈24/s`）→ 纯计算 |
| 用户实例的 3 个渲染进程 | **0%** | — | 用户没在交互时渲染进程闲置，排除渲染侧死循环 |
| 我这一轮工作期间 | 12–25% → **0%（我一停就归零）** | — | 服务进程的 CPU **跟着活跃会话走**，不是常驻后台循环 |

活跃会话：5 分钟内唯一在被写入的 `session.v4.jsonl.zstd` 是**当前这个 agent 会话**（已 5.2 MB）。
用户自己的会话规模也不小：185 个会话共 **201.5 MB**，最大的 **22.9 MB**。

## Conclusion

- **不是壳的基线开销**：同一个壳 + 我们的插件在空数据目录下 0% CPU、57 MB。
- 卡顿与**活跃会话的工作量**同相：agent 在跑（工具调用、记录写入、事件推流）时服务进程 12–25%，
  一停就掉到 0%。用户打字时的 UI 更新要经过同一个服务进程，所以「我在干活时他打字卡」是可预期的。
- 大记录本身就是成本：单会话 20 MB 级别意味着每次渲染/推流都要处理很长的历史。
- 我这一整天在同一实例里跑构建、打包 200 MB 安装包、起多个 Electron 实例，也是这台机器负载的一部分
  （诚实归因；这些实例都已杀掉）。

## Alternatives considered

- **怀疑渲染进程死循环**（最强理由：打字延迟通常就是界面线程被占）→ 实测三个渲染进程在非交互期间为 0%，
  排除。
- **怀疑某个插件在轮询**（最强理由：扫到 `dsh-run-env-manager` 客户端 `POLL_INTERVAL_MS = 2e3`、
  `dsh-git-panel`/`dsh-plugin-kit` 多处 `setTimeout(fn, 0)`，且用户 profile 开了 `patchReload: live`）→
  用 0.5 秒采样否掉了「2 秒定时器」这个形状：真实的 25% 是**连续**的；且 `ReadOps=0` 与「文件监视/轮询
  进程状态」这类解释不符。插件的代价仍是**待查项**，只是不在这次的证据里。
- **直接重启用户的实例做 A/B**（最强理由：能干净地逐项排查）→ 放弃：我的会话跑在那个实例里，重启会打断
  自己，也会打断用户正在做的事。改成「空数据目录对照 + 不重启采样」。

## 附带的两个产品事实（本轮一并确认）

1. **工作区是服务端按 DSH 数据目录存的**（`<home>/storages/workspace.json`）：手机看到的工作区取决于
   它连的那个 DSH 用哪个 home。用户先前看到「手机工作区和 PC 不一样」，是因为他连的是我的**测试实例**
   （临时 home，注册表里只有 1 条默认工作区），而他的应用用 `~/.dsh`（26 个工作区）。产品形态下手机连的是
   应用自己的网关 → 同一个服务进程、同一个 home → 同一份工作区，**不需要改代码**。
2. **用户的实例已经从 0.4.0 升到 0.4.1**，自己开了局域网访问（`pocket: [局域网] 网关已启动
   http://10.1.6.35:41730`），手机登录来自 `10.1.5.40`，并且防火墙规则里出现了 `Any` 配置文件的一项
   （即用上了新的一键放行链路）。

## Consequences

- 「卡」这类反馈从此有可复用的量法：**先量再说**，而且要在用户正在用的实例上量（重启会破坏现场，也会打断
  agent 自己）。
- 采样频率本身是结论的一部分：3 秒粒度会把连续占用误判成周期任务，本次差点把方向带偏。
- 空数据目录对照是一个便宜的基线工具（同壳、同插件、空 profile），以后任何「壳是不是变慢/变重了」的问题
  都先用它量一次。
- 单会话记录的体量（本例 5.2 MB 活跃 + 用户最大 22.9 MB）是**用户可见的性能因素**：值得在界面上给会话
  体积一点可见性（例如过大时提示另开新会话），但那属于 DSH 侧的行为，不在壳里改。

## Evidence

- 采样脚本输出（0.5 秒粒度，24 格）：服务进程 25/28/25/28… 渲染进程全 0。
- 空数据目录实例：`空闲 CPU: 0%  内存: 57 MB`。
- `Win32_PerfFormattedData_PerfProc_Process`：`ReadOps=0 OtherOps=24 DataOps=0`。
- 会话文件：`sessions/--D-workspace-research-deepseek-harness-desktop--/session-2b06d771-…/session.v4.jsonl.zstd`
  0.2 秒前写入，5.2 MB；用户会话总计 201.5 MB / 185 个。

## 第二轮的定量：把「打字延迟」量到帧上

第一轮只量了进程 CPU，而**「渲染进程 0%」是在用户不交互时量的**——那正好量不到渲染开销，结论不完整。
用户补充症状后（打字延迟约 0.5 秒、切换会话掉帧），换成在**页面内部**量：

- 手段：把用户的会话数据**复制**一份（200 MB → 475 MB 含缓存），用同一个壳带
  `--remote-debugging-port` 起实例，通过 CDP 在页面里记录 `requestAnimationFrame` 间隔，并用
  `Input.insertText` 注入真实输入（脚本：`electron/scripts/probe-typing-latency.mjs`）。
- **空闲态**（会话已打开、无 agent 运行）：DOM 3697 节点，帧 **平均 16.5 ms / p95 16.8 ms / 零慢帧**，
  每字符约 9 ms —— 60fps，健康。
- **流式输出态**（我自己这一轮正在往页面推流时，测量用户实例的渲染进程）：会话页渲染进程
  **58–158%（峰值超一个核）**，同期服务进程 4–25%，其它视图 0–7%。
- 会话页渲染进程常驻内存 **395 MB**（长会话的 DOM/堆）。

结论升级为：**慢的是「渲染超长会话 + 正在流式输出」这个组合**。用户打字时正好在这个组合里（他在读我的
回复时回我），按键要等渲染线程；没有任何 agent 在跑时界面是健康的 60fps。壳本身仍无可测量的贡献。

### 可执行的部分

- 产品层面这是 DSH **客户端**的渲染成本（消息列表未虚拟化），不在壳里能修的范围；要修得动上游。
- 用户侧：把工作拆到更短的会话里（他最大的会话 22.9 MB，我这个 5.2 MB），超大会话不要长期开着。
- 我这边：**减少自己的推流量**——回复更短、不要把大段日志/图片堆进会话，这直接降低那 100%+ 的渲染占用。

## 第三轮（2026-10-18）：根因是 genui 0.12.0 的 DOM 围栏发现，不是壳、也不是 DSH 核心

用户再次报告「会话运行中或刚运行完时掉帧严重」。上一轮把成本归到「超长会话 + 流式输出」的 DSH
渲染；这一轮用**去掉桌面壳的对照实例**把插件层单独量了出来，结论要改写。

方法（完整数据与探针脚本留在本机 `.tmp-perf/`，按 `.gitignore` 不入库）：

- 用 `electron/runtime/dsh` 独立启动同一版本的 DSH（`DSH_HOME` 指向用户 `~/.dsh` 的副本，独立端口），
  在**普通 Electron 44 窗口**里打开（无 `--patch` overlay、无 `dsh-desktop-shell` 注入），CDP 量帧、
  长任务、打字延迟和 CPU profile；
- 会话选用户最大的 `坦克世界风格3D坦克对战游戏`（22.9 MB，DOM 18,707 节点，`<span>` 6,925）；
- A/B：原样 / 移除 genui bundle / 升级 genui 0.13.0。

| 配置 | 空闲 3 秒 | 长任务 | 打字 6 字符 | CPU profile |
|---|---|---|---|---|
| genui 0.12.0（用户当前） | max 帧 450.5 ms | 455/459/464 ms，每 1 s 一组 | 408 ms/字符 | 42.2% 在 genui `sweep`（`Tv`/`te`/`rv`），`hasAttribute` 9.5% |
| 移除 genui | max 17.9 ms（60fps） | 0 | 正常（约 11 ms/字符） | 99.8% idle |
| genui 0.13.0 | max 17.7 ms（60fps） | 0 | 正常 | 99.8% idle |

机制（`@changfenhuang/dsh-genui@0.12.0` 的 `src/client/dom-fence.tsx`）：

- `MutationObserver` 挂在 `document.body`（`childList` + `subtree` + `attributes(data-streaming)` +
  `characterData`），另有 `setInterval(sweep, 1000)`（`:1142-1173`，`SWEEP_MS = 1000` 在 `:103`）；
- 每次 `sweep()` 都跑 `findFenceCandidates()`（`:369-423`），对整个文档做三趟查询：代码块表面、
  所有 `<pre>`、**所有 `<span>`**；每个 span 还要两次 `closest()` + `tagTextBodyOf()`；
- 成本 ≈ O(已加载对话 DOM)：3,264 节点约 5 ms（无感），18,707 节点约 450 ms；
- 流式时 `characterData` 的每条变更都会 `schedule()` → 每帧一次全文档 sweep；空闲时靠 1 s 定时器
  兜底。于是「运行中」和「刚运行完」都在掉帧，而小会话完全看不出来。

判定：**掉帧是第三方插件 `@changfenhuang/dsh-genui@0.12.0` 引起的**。

- 桌面壳：本轮测量里壳代码根本没有参与（无 overlay、无 shell client），掉帧照旧；壳侧另有
  「主进程 0% CPU、每回合只改一次状态与 setBounds、无每帧 IPC」的静态与日志证据（本轮壳侧排查记录
  留在本机 `.tmp-perf/`，未入库）。
- DSH 核心：同一 DSH、同一会话、同一窗口，只移除 genui 就回到 60fps；DSH 的流式发布本身是
  rAF 合批（`dsh-client-ui-conversation` 三重 rAF），不是每 token setState。
- 上一轮「壳无贡献、卡在超长会话 + 流式」的方向没错，但把「超长会话」记成了 DSH 渲染成本；
  真正的放大项是插件对超长 DOM 的全量扫描——DSH 未虚拟化只是让这个 O(DOM) 插件变贵的背景条件。

修复：

1. 短期：壳内插件市场把 `@changfenhuang/dsh-genui` 升级到 **0.13.0**（同一大会话实测 60fps、0 长任务；
   其 CHANGELOG 明写「DOM 围栏发现改为跟踪页面变更，减少对话内容的重复扫描」，代码改为 dirty target
   + `SWEEP_BUDGET_MS` 时间预算 + 分片 `rotationSweep`）。
2. 不能升级时：从 `dsh-desktop` profile 的 bundles 移除 genui（代价是正文里的 dsh-ui 围栏回退成代码块）。
3. 插件侧长期：DOM 通道的观察范围应从 `document.body` 缩到对话滚动容器；`span` 通检要有证据门槛
   （只有出现 tag-text 候选才跑）；sweep 必须有时间预算（0.13.0 已做前两项中的跟踪与预算）。

## 下一步

第三轮已经回答了「没有 agent 在跑也卡」：是 genui 的 1 s 全量 sweep。以后任何「掉帧」反馈，
先用本机 `.tmp-perf/probe/` 里的探针脚本（未入库）在**去掉壳的独立实例**里量三件事：长任务节奏、CPU profile 的调用栈归属、
以及插件 bundle 的 A/B；比按进程 CPU 猜快得多。
