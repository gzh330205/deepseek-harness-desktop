# Agent Note: 随包 DSH 运行时升级到 0.2.1-rc.1（含插件兼容性核查）

Status: implemented

> 已被 [2026-10-18-dsh-runtime-0-2-1-rc2.md](2026-10-18-dsh-runtime-0-2-1-rc2.md) 取代：rc.2 当时缺的包已补齐，
> 壳 0.4.3 起随包运行时为 0.2.1-rc.2。本文保留 rc.1 阶段的兼容性核查与真机验证记录。

## Problem

随包运行时钉在 dsh `0.2.0-rc.2`，上游已发布 0.2.1 系列。升级不是改一个版本号：随包运行时是**壳的一部分**
（`runtime-pin.json` + `runtime/dsh` 整棵树 + `desktop-runtime.json` 清单），而用户 profile 里装的插件是按
旧运行时开发的，升级会同时考验两端。

## Decision

**升到 `0.2.1-rc.1`，不是最新的 `0.2.1-rc.2`。**

理由：`0.2.1-rc.2` 是**发了一半的版本**——`@deepseek-ai/dsh-client-ui-settings-account` 只发到 `0.2.1-rc.1`，
所以 rc.2 的依赖树装不出来（`npm install` 报 `ETARGET`）。我先怀疑是本机 npm 缓存/代理陈旧（用全新 cache
目录对照验证过一次），最后用 registry 元数据确认是上游缺包：rc.2 的 78 个钉死依赖里那个包没有 rc.2。
rc.1 的依赖树完整（实测安装成功），因此取 **最新完整的 rc**。

## 升级过程

1. `runtime-pin.json`: `dsh` → `0.2.1-rc.1`（`pnpm/node` 不动）。
2. `node scripts/prepare-runtime.mjs`（需要 `PATH` 前缀 `C:\Windows\System32`：Git Bash 的 GNU tar 会把
   `D:\…` 当成远程主机）。产物：**24240 个文件 / 545.8 MiB**（旧版 12096 / 440.6 MiB，约 +100 MB）。
3. 壳版本 0.4.1 → **0.4.2**：`release-electron.mjs` 的闸门要求 `desktop-runtime.json.shell === version`，
   否则「运行时是为别的版本构建的」直接失败；所以改版本号后要重跑一次 prepare-runtime（第二次走缓存，快）。
4. 全量测试 460 条 / 452 通过 / 0 失败；类型检查干净。

## 插件兼容性核查

### 静态

- 8 个插件的 `package.json` peer 范围是 `@deepseek-ai/dsh-settings|dsh-tools: >=0.1.0-rc.7 <0.3.0`
  → **0.2.1-rc.1 在范围内**，无需改 peer。
- 插件里 `from '@deepseek-ai/...'` 的包名逐个对照新运行时：**全部存在**。
- 插件用到的服务/插槽名（`settings.section`、`settings.plugins.tab`、`sidebar.right.pane.tab`、
  `sidebar.workspaces`、`webServer`、`uiSession`、`systemPrompt` 等）在新运行时里逐个 grep：**全部存在**。
- 用户 profile 的 `cordis.patch.yml` 引用了 38 个 `@deepseek-ai/*` 包：**全部还在**。

### 唯一发现的破坏：`dsh-experimental-agent-team-web-profile` 没了

真实启动（见下）报：

```
dsh: skipping profile bundle "@deepseek-ai/dsh-experimental-agent-team-web-profile":
     Error: dsh: cannot resolve profile bundle
```

0.2.1 里这个 bundle 被**合并**进 `@deepseek-ai/dsh-experimental-agent-team-profile`（后者现在依赖
`dsh-experimental-client-ui-agent-team`），所以功能不丢，**把失效条目从 profile 的 bundle 列表删掉即可**。
两个 profile（`dsh-desktop`、`dsh-desktop-dev`）都已修，改前各自备份为
`package.json.bak-dsh021-<时间戳>`。

### 真机（本机）验证方式

复制一份用户 profile（17 MB，插件大多是 symlink 到开发目录）到临时 `DSH_HOME`，用

用户全部插件**一起加载：

- 主机侧：我们的插件、`dsh-win-notify` 等都正常 apply；除上面那个 bundle 外无其它错误。
- 客户端侧（CDP 查页面）：标题正常、**没有** `Failed to load plugins`、150 个插件相关节点、
  **0 条运行期异常/console.error**。
- 各插件自己的测试：`dsh-mcp-skill-manager` 23/23、`dsh-workspace-category-manager` 通过、
  `dsh-run-env-manager`/`dsh-git-panel`/`dsh-win-notify`/`dsh-sidebar-width` 通过；
  `dsh-oneway-usage-monitor`、`dsh-plugin-kit` 没有 test 脚本（`npm test` 退出码 1 是**没有脚本**，不是失败）。
- 客户端插件重新构建 `lib/client.js`：产出与仓库一致（git 无 diff），构建链没坏。

### 插件开发目录的更新

- `dsh-oneway-usage-monitor/` 是 `.gitignore` 里**故意不入库**的本地插件（仓库注释写明），所以它的改动只在本机。

## 发布

**v0.4.2 已发布**并完成匿名复核：安装包 223.30 MB（0.4.1 是 214.6 MB）、`.sig`、`DSH.Pocket.apk` 3.39 MB
（sha256 与清单一致）、`latest.json` 版本 0.4.2。发布说明写明了运行时升级到 0.2.1-rc.1 与 bundle 引用修复。
发版闸门（版本一致、运行时 `shell` 字段一致、打包 + 打包态 smoke、签名自校验）全部通过。

## Alternatives considered

- **直接升 0.2.1-rc.2**（最强理由：最新 rc，"rc" 听起来就是该用的那个）→ 弃：该版本依赖树缺包，装不出来。
  我把「本机缓存陈旧」和「上游缺包」分开验证过（全新 npm cache + 直接读 registry 元数据），结论是后者。
- **只改 `runtime-pin.json` 不重跑 prepare-runtime** → 弃：`desktop-runtime.json` 会留着旧版本，发版闸门
  会拦（`shell` 字段不一致），而且发行包里会是旧树配新版本号——正是闸门要防的那种「静默发旧」。
- **改 profile 的 bundle 列表时顺手清理其它历史条目**（`package.json.bak-*` 等备份文件、dev 渠道的旧条目）→
  弃：这次只做「让它在 0.2.1 下跑起来」的最小改动，用户自己的备份文件不动，避免把别人的工作现场当垃圾清掉。
- **把 `dsh-sidebar-width` 也装进 profile**（仓库里有、profile 里没装）→ 弃：它可能是未完成品，装不装是用户
  的选择，我只报告这个事实。

## Consequences

- 安装包会明显变大：运行时 440.6 MiB → 545.8 MiB（+约 100 MB，压缩后仍会显著增长）。这是升 DSH 的必然代价，
  发布前应告知用户。
- 以后升运行时：改 pin → prepare-runtime → 改壳版本 → 再 prepare-runtime（因为闸门比对 `shell` 字段）→
  全量测试 → 打包 dry-run。
- profile 的 bundle 列表属于**用户数据**：我们只能提示/修复，不能保证它随版本自动迁移；上游改名一次就会有
  一条「skipping profile bundle」，好在 dsh 只跳过、不失败。
